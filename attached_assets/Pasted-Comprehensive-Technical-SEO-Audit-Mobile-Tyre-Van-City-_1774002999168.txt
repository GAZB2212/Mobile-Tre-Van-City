Executive Summary

This audit was conducted in response to a low Ahrefs Health Score of 30/100 and a high volume of reported page errors. A full crawl, raw HTML inspection, and Google PageSpeed Insights analysis were carried out across all 17 pages of the site.

The root cause of the majority of Ahrefs errors is the site's Client-Side Rendering (CSR) architecture. The site is built as a React Single Page Application (SPA), meaning the server delivers a near-empty HTML file to crawlers and search engines. All visible content — headings, body text, images, and links — is generated by JavaScript after the page loads. SEO tools and many search engine crawlers cannot execute JavaScript, so they see the pages as empty, which triggers a cascade of errors including missing H1 tags, missing content, missing internal links, and missing structured data.

Beyond the architecture issue, there are additional critical problems: duplicate content from unredirected www and non-www versions, soft 404 errors, severely unoptimised images, a 1.78 MB uncompressed JavaScript bundle, and a complete absence of Open Graph tags and structured data. Together, these issues explain the low Ahrefs score and will be preventing the site from ranking competitively on Google.

The good news is that all of these issues are fixable. This report details every finding with a severity rating and a clear, prioritised action plan.

Section 1: Architecture — The Root Cause of Most Errors

1.1 Client-Side Rendering (SPA) — Severity: Critical

The single most important finding in this audit is that the website is built as a Client-Side Rendered React Single Page Application. When a search engine crawler or an SEO tool like Ahrefs requests any page on the site, the server returns the following minimal HTML:

HTML


<html lang="en-GB">
  <head>
    <title>Mobile Tyre Van Conversions UK | Custom-Built & Ready to Earn</title>
    <meta name="description" content="...">
    <script src="/assets/index-CS7F4031.js" type="module"></script>
    <link href="/assets/index-BK7Jxuf9.css" rel="stylesheet">
  </head>
  <body>
    <div id="root"></div>
  </body>
</html>



The <body> contains nothing but an empty <div>. Every heading, paragraph, image, and link that a visitor sees is injected by the JavaScript file after the browser has loaded and executed it. This means:

•
Ahrefs, Screaming Frog, and most SEO tools see 0 H1 tags, 0 H2 tags, 0 images, and 0 internal links on every page.

•
Google's primary crawl bot (Googlebot) can render JavaScript, but it does so in a secondary indexing queue that can lag weeks behind the initial crawl.

•
The site's text content is effectively invisible to the majority of the SEO ecosystem, which is why Ahrefs is reporting so many errors.

Recommendation: Migrate the site to Server-Side Rendering (SSR) using a framework such as Next.js (which is React-based and would require the least rewriting). With SSR, the server sends a fully rendered HTML page with all content already present. This would resolve the vast majority of Ahrefs errors in a single change. An alternative is to implement a dynamic rendering proxy (such as Prerender.io) that serves pre-rendered snapshots to bots while keeping the SPA experience for real users.




Section 2: Duplicate Content and URL Canonicalisation

2.1 www vs Non-www Duplicate Content — Severity: Critical

Both of the following URLs return a 200 OK response and serve identical content:

•
https://www.mobiletyrevancity.co.uk/

•
https://mobiletyrevancity.co.uk/

There is no 301 redirect from one to the other. From Google's perspective, these are two separate websites with identical content. This splits the domain's authority and ranking power across two versions, weakening both.

Recommendation: Implement a permanent 301 redirect at the server level from https://mobiletyrevancity.co.uk/ to https://www.mobiletyrevancity.co.uk/ (or vice versa ). The canonical version should also be specified consistently in all <link rel="canonical"> tags.

2.2 Missing Canonical Tag on Homepage — Severity: High

The homepage (/) does not include a <link rel="canonical"> tag in the raw HTML. All other pages do have canonical tags, but the homepage is the most important page on the site and is missing this signal.

Recommendation: Add <link rel="canonical" href="https://www.mobiletyrevancity.co.uk/" /> to the homepage <head>.

The Privacy Policy, Terms & Conditions, and Cookie Policy pages all share the homepage's title tag and meta description. These pages are using the default fallback rather than unique metadata.

Section 3: HTTP and Technical Errors

3.1 Soft 404 Errors — Severity: Critical

When a user or crawler visits a URL that does not exist on the site (e.g., /this-page-does-not-exist ), the server returns an HTTP 200 OK status code instead of a 404 Not Found code. The React router handles the "not found" state on the client side, but the server itself reports success.

This is known as a Soft 404 and is a significant problem for SEO. Google will attempt to index these non-existent pages, waste crawl budget on them, and may penalise the site for serving low-quality content with a 200 status.

Recommendation: Configure the server to return a proper HTTP 404 status code for any URL that does not correspond to a valid route. This is a server-side configuration change.

The main HTML pages are served with cache-control: private, max-age=0, meaning they are never cached by browsers or CDNs. 4.3 Performance Issues and Savings

The following issues are directly causing the poor load times, listed in order of impact:

Issue 1 — Uncompressed JavaScript Bundle (1.78 MB)
The main JavaScript file is 1.78 MB and is served without Gzip or Brotli compression. Enabling compression would reduce this to approximately 400–500 KB, a saving of over 1.3 MB on every page load. Additionally, 74% of the code in this bundle (1.32 MB) is unused on the initial page load and should be split into smaller chunks loaded on demand.

Issue 2 — Render-Blocking CSS (114 KB)
The main stylesheet (index-BK7Jxuf9.css) is 114 KB and is loaded in a way that blocks the page from rendering for 2,130ms on mobile. Of this, 90 KB is unused CSS from the Tailwind CSS framework that was not purged during the build process.

Issue 3 — Massive Unoptimised Images (15.5 MB total)
The total network payload for the homepage is 15.5 MB, the vast majority of which is images. Individual images are being served as large JPEGs and PNGs without compression or format optimisation:

Issue 4 — Google Fonts Render-Blocking
Google Fonts CSS is loaded synchronously and blocks rendering for 800ms on mobile. Using font-display: swap and preloading the font files would eliminate this delay.

Issue 5 — No Preload for LCP Image
The Largest Contentful Paint element is a hero image that is not discoverable until the JavaScript has executed. Adding a <link rel="preload"> tag for this image in the HTML <head> would significantly reduce LCP time.

No Open Graph or Twitter Card meta tags exist on any page of the site. When a link to the site is shared on Facebook, LinkedIn, WhatsApp, or Twitter, no image, title, or description preview will appear — just a plain URL. This significantly reduces click-through rates from social media.

5.6 Internal Linking — Severity: High (due to SPA)

Because the site is a SPA, all internal links are rendered by JavaScript and are invisible to crawlers in the raw HTML. The navigation menu, footer links, and in-page CTAs all exist only in the rendered DOM. Once SSR is implemented, these links will be crawlable and will distribute PageRank across the site correctly.

Additionally, there is no blog or content hub, which means there are very few internal linking opportunities between pages. A blog would significantly improve internal link architecture and keyword targeting.
